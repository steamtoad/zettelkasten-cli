# Design: исправление регрессий атомарной записи

## Context

Пять воспроизведённых дефектов описаны в evidence.md. Scope ограничен восстановлением и уточнением одиночной файловой безопасности. Обязательства полного транзакционного recovery не переносятся из другого change.

## Decisions

### 1. Владение назначением при Refine rollback

Неуспешный exclusive create не даёт права удалять назначение. Refine должен различать существовавший/чужой путь и новый объект, созданный этой попыткой. Rollback удаляет только созданное этой попыткой назначение; если его identity уже не совпадает, путь сохраняется и диагностируется конфликт. Одна проверка `-e` до записи не заменяет exclusive reservation и учёт владения. Нужны CLI fixtures обычного файла, live/dangling symlink и конкурента между preflight и reservation.

### 2. Подготовка данных и проверка producer

Full Copy сначала завершает проверяемую подготовку successor, затем резервирует новое назначение и записывает подготовленный файл с контролем ошибок. Обрабатываются пустой stdout с ненулевым статусом и частичный stdout с ненулевым статусом. Один `pipe_fail` полезен, но сам по себе не подтверждает корректность опубликованного документа и cleanup. Нельзя печатать success или переходить к deprecation после отказа обязательного шага. Проверка metadata producer внутри command group должна происходить до завершающих print, которые иначе маскируют ошибку.

Это не обещает rollback всех предыдущих независимых записей. Уже затронутые файлы учитываются в диагностике согласно WRITE-SAFE-002.

### 3. Политика свойств файла

До замены writer определяет mode, owner/group и наличие ACL через поддержанный механизм платформы. Для поддержанной политики воспроизводит свойства на prepared file и проверяет результат до replace. Если политика, инструмент обнаружения или воспроизведение свойств не поддержаны, возвращает явный ненулевой результат до replace. Отсутствие инструмента не означает отсутствие ACL.

В реализации необходимо явно документировать, какие ACL/ownership cases поддержаны на macOS и Linux. Минимально совместимая реализация может отклонять обнаруженные ACL вместо их переноса; молчаливое удаление запрещено. Этот change не требует privileged chown, не меняет ownership чужих файлов для обхода ошибки и не обещает сохранение всех произвольных xattrs/flags. Для обычного поддержанного файла без ACL успешная запись остаётся доступной.

### 4. Topic preflight

Прямой constructor и `zk_topic_write` используют согласованный preflight обязательных title/key-topic до первой записи. Сохраняются прежние правила допустимого непустого текста; constructor не подменяет переданный ключ заголовком или description. Пустой ключ отклоняется при standalone и sourced вызове. Нормализация whitespace и защита всех полей от header injection не добавляются из соседнего change.

### 5. Диагностика затронутых файлов

Учёт начинается с первой реальной knowledge-записи, в том числе создания `all-todays` до создания successor. Пути абсолютные либо однозначно относительно ZK_HOME. При ошибке список охватывает все созданные/изменённые этой попыткой knowledge-файлы, включая существовавший либо новый журнал. Подготовленные recovery-файлы, если сохранены, перечисляются отдельно. Незатронутые кандидаты не выдаются за уже изменённые.

Тест сравнивает диагностированный набор с snapshot/hash diff fixtures, а не только заголовок сообщения. Полная транзакция и восстановление журнала автоматически этим change не обещаются.

## Compatibility and Architecture

Neutral primitives остаются в `.scripts/lib/`; input preflight Topic — в object layer; Refine/Reduce sequencing и changed-files принадлежат host workflows. UUID/link targets, :type:, :key-topic:, :deprecated: и activity format не меняются. Valid input сохраняет существующее поведение. L1 fixes не требуют перестройки plugins.

## Failure and Git Safety

Все негативные fixtures живут во временном ZK_HOME. При collision проверяются bytes, mode и symlink target до/после; чужое назначение не удаляется ради cleanup. При unsupported metadata и отказе подготовки исходные свойства остаются прежними. При ошибке replacement возвращается ненулевой статус и указывается сохранённый recovery artifact, если он есть. Source changes не смешиваются с migration или commit/tag/push.

## Alternatives

- Только дополнить инструкции агенту: недостаточно, дефекты воспроизводятся через CLI.
- Проверить лишь exclusive helper: пропускает удаление назначения вызывающим rollback.
- Проверить лишь consumer pipeline: пропускает отказ Full Copy producer.
- Копировать только mode: нарушает явно принятую ACL/ownership policy.
- Ввести общий transaction manager: выходит за scope; отдельный change сохраняет владельца TXN requirements.

## Integration

Сначала добавить failing behavioral tests; затем минимальные fixes. Синхронизировать пять полных MODIFIED blocks, legacy формулировки/status и Feature List только по результатам проверки; сохранить exact-once ID parity. Перепроверить predecessor verification и готовность обеих дельт. Архивирование остаётся отдельной операцией после устранения противоречий.
