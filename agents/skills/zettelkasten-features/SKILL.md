# zettelkasten-features

## Назначение

Сопоставлять фактическую реализацию `zettelkasten-cli` с каноническим feature list, предлагать обновления после успешной проверки изменённых скриптов и документировать крупные функциональные изменения отдельными связанными Note.

## Пути

- Zettelkasten: `/Users/steamtoad/zettelkasten`
- Скрипты: `/Users/steamtoad/zettelkasten/.scripts`
- Канонический feature list: `/Users/steamtoad/zettelkasten/.scripts/docs/features.adoc`
- Канонические требования: `/Users/steamtoad/zettelkasten/.scripts/docs/requirements.adoc`

## Когда применять

Применять после запросов о проверке или изменении скриптов, обсуждения новой фичи, нового скрипта или существенного изменения поведения. Типичные формулировки:

- «я изменил скрипты, проверь»;
- «добавлена новая фича»;
- «нужно ли обновить feature list?»;
- «примени изменения в списке фич»;
- «обнови features.adoc».

Если пользователь просит только аудит и запрещает изменения, показать предлагаемые правки, но не менять файлы.

## Условие предложения обновлений

Предлагать изменения `features.adoc` только после того, как изменённые скрипты прошли доступные проверки и не обнаружено ошибок.

Минимальные проверки:

1. `zsh -n` для изменённых CLI-скриптов и затронутых библиотек.
2. `zt-check` для проверки целостности Zettelkasten.
3. Целевые временные тесты для изменённого поведения, если статического анализа недостаточно.
4. Проверка того, что тесты не изменили рабочий Zettelkasten.

Если проверки выявили ошибку, сначала сообщить об ошибке и не предлагать новую возможность как реализованную.

## Правила feature list

- `features.adoc` описывает только подтверждённую текущую функциональность.
- Не включать roadmap, пожелания и предполагаемое поведение как реализованные фичи.
- Формулировать фичи в границах фактической реализации и явно указывать существенные ограничения.
- Сохранять стабильные идентификаторы существующих фич, если их смысл не изменился.
- Добавлять новый ID только для новой самостоятельной возможности.
- Если фича больше не реализована, удалить её или описать изменение после подтверждения поведения.
- Не дублировать одну возможность в нескольких разделах без различия пользовательского поведения и внутреннего механизма.
- Полностью поддерживать `features.adoc` как самодостаточный актуальный документ, а не журнал патчей.
- Обновлять файл только после явного запроса применить согласованные изменения. После обычной проверки скриптов показывать предлагаемые правки отдельно.

## Классификация изменений

Крупное функциональное изменение:

- появился новый пользовательский скрипт или самостоятельная новая фича, которой раньше не было;
- существенно изменилось поведение нескольких существующих фич;
- изменена модель связей, документов или основной пользовательский workflow.

Не является крупным функциональным изменением:

- исправление ошибки;
- внутренний рефакторинг без изменения поведения;
- уточнение формулировки feature list;
- изменение одной небольшой существующей фичи;
- форматирование или техническое обслуживание.

При сомнении сначала объяснить классификацию пользователю. Не создавать Note для обычного исправления ошибки.

## Процесс обновления

1. Прочитать текущий `features.adoc`, изменённые скрипты, библиотеки и связанные требования.
2. Проверить синтаксис, целостность и фактическое поведение.
3. Сопоставить реализацию с существующими ID фич.
4. Показать пользователю:
   - новые фичи;
   - изменившиеся формулировки;
   - удалённые или больше не подтверждённые фичи;
   - известные ограничения.
5. После явного запроса применить изменения полностью обновить `features.adoc`.
6. Определить, является ли изменение крупным функциональным изменением.
7. Если изменение крупное, создать отдельную Note с описанием:
   - что появилось или существенно изменилось;
   - какие пользовательские сценарии теперь поддерживаются;
   - какие фичи и требования затронуты;
   - какие ограничения остались;
   - как поведение было проверено.
8. Для созданной Мартой Note использовать:
   - `:type: note`;
   - ключевое слово `note`;
   - `:author: marta`;
   - `:generated-at: YYYY-MM-DD`;
   - UUID v1 как имя файла;
   - относительные AsciiDoc-ссылки;
   - `:key-topic: Разработка Zettelkasten CLI`.
9. Найти последнюю Note, описывающую крупное изменение функциональности или предыдущую редакцию feature list:
   - добавить в новую Note ссылку `Предыдущее изменение`;
   - добавить в старую Note ссылку `Следующее изменение`;
   - не помечать старую Note deprecated, если пользователь отдельно этого не просил.
10. Связать новую Note двусторонними ссылками с недавними тематическими Note, Memo и Topic, непосредственно относящимися к изменённой функциональности.
11. Добавить новую Note в `all-todays/YYYY-MM-DD.adoc`.
12. Запустить `zt-check` и сообщить короткий результат.

## Безопасность

- Не менять скрипты при работе только с feature list.
- Не объявлять ошибочное или непроверенное поведение реализованной фичей.
- Не создавать Note для каждого исправления ошибки.
- Не переименовывать существующие UUID и файлы.
- Не перезаписывать пользовательские незакоммиченные изменения.
- Не добавлять нерелевантные кросс-ссылки только из-за совпадения общих тегов.
