# zettelkasten-requirements

## Назначение

Обновлять каноническую спецификацию `zettelkasten-cli` и сохранять каждую редакцию требований отдельной Note в Zettelkasten с историей изменений и перекрёстными ссылками.

## Когда применять

Применять навык, когда пользователь просит проверить, валидировать, уточнить или применить требования после обсуждения новой фичи, нового скрипта или изменения поведения. Типичные формулировки:

- «вот новый скрипт или описание фичи, нужно ли обновить требования?»;
- «проверь требования»;
- «примени требования с правками»;
- «примени требования без правок»;
- «обнови спецификацию zettelkasten-cli».

Если пользователь просит только анализ и явно запрещает изменения, показать предложения, но не обновлять файлы.

## Источники и пути

- Zettelkasten: `/Users/steamtoad/zettelkasten`
- Каноническая спецификация: `/Users/steamtoad/zettelkasten/.scripts/docs/requirements.adoc`
- Скрипты: `/Users/steamtoad/zettelkasten/.scripts`

## Структура требований

Каждое требование имеет стабильный идентификатор и один статус:

- `INVARIANT` — обязательное свойство, нарушение которого может повредить хранилище или совместимость;
- `IMPLEMENTED` — подтверждённое текущее поведение;
- `PROCESS` — правило разработки, миграции или проверки;
- `ROADMAP` — целевое, ещё не обязательное поведение.

Не смешивать реализованное поведение с roadmap. Не объявлять требование `IMPLEMENTED` без проверки кода или поведения.

## Процесс обновления

1. Прочитать текущий `requirements.adoc` и связанные с обсуждением скрипты, заметки и планы.
2. Проверить фактическое поведение. Для спорных или опасных инвариантов использовать временный тестовый Zettelkasten, не рабочее хранилище.
3. Сопоставить изменения с существующими требованиями:
   - сохранить стабильные ID, если смысл требования сохраняется;
   - изменить формулировку или статус, если фактическое поведение изменилось;
   - добавить новый ID только для нового самостоятельного правила;
   - удалить требование только с явным объяснением причины и последствий.
4. Полностью обновить канонический `.scripts/docs/requirements.adoc`. Документ всегда должен оставаться самодостаточной актуальной спецификацией, а не патчем или журналом изменений.
5. Создать отдельную Note, содержащую полный снимок новой редакции требований.
6. Для созданной Мартой Note обязательно использовать:
   - `:type: note`;
   - ключевое слово `note`;
   - `:author: marta`;
   - `:generated-at: YYYY-MM-DD`;
   - UUID v1 как имя файла;
   - относительные AsciiDoc-ссылки вида `link:UUID.adoc[Название]`;
   - `:key-topic: Разработка Zettelkasten CLI`.
7. Найти последнюю активную Note-редакцию требований:
   - добавить ей `:deprecated:` только в заголовок AsciiDoc;
   - добавить в старую Note ссылку `Следующая редакция` на новую;
   - добавить в новую Note ссылку `Предыдущая редакция` на старую;
   - не архивировать тематические Note, Memo или Topic, которые не являются предыдущей редакцией требований.
8. Связать новую Note двусторонними ссылками с недавними заметками, непосредственно относящимися к изменённым требованиям: Topic разработки CLI, feature list, планы, Memo о соответствующих скриптах и фичах. Не добавлять нерелевантные ссылки только из-за совпадения общих тегов.
9. Добавить новую Note в текущий `all-todays/YYYY-MM-DD.adoc`.
10. Проверить результат:
    - новая и старая редакции образуют двустороннюю последовательную цепочку;
    - старая редакция deprecated, новая активна;
    - канонический файл и новая Note содержат одну редакцию требований;
    - ссылки относительные и не битые;
    - псевдометаданные в `[source]`-блоках не изменены;
    - `zt-check` завершается без ошибок.
11. Показать короткий отчёт: какие требования изменены, какая Note создана и архивирована, с какими заметками установлены связи, результат проверки.

## Правила безопасности

- Не менять скрипты при обновлении требований, если пользователь отдельно не просил изменить реализацию.
- Не перезаписывать пользовательские незакоммиченные изменения.
- Не переименовывать существующие UUID и файлы.
- Не помечать deprecated обычные Note, Memo или Topic из-за обновления спецификации.
- Предыдущей редакцией считать только последнюю активную Note, явно являющуюся снимком требований.
- Если каноническая спецификация и последняя Note расходятся до начала работы, сначала сообщить о расхождении и определить актуальный источник по контексту обсуждения и фактическому коду.
- Если пользователь говорит «примени без правок», не менять формулировки сверх уже согласованной редакции.
